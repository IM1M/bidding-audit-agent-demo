# 设计文档

## 项目背景

当前企业招标采购审核面临双重效率瓶颈：专家产能不足（单份文件3.5小时，年处理数千个采购包）和质量风险高（专家尺度不一，审计不可追溯）。系统需在满足等保三级、国密算法、信创适配等合规要求的前提下，将四道人工审核（采购需求、招标文件、投标资格、评标报告）自动化，提升效率65%以上。

核心约束：
1. "数据不出域"：原始文件、条款向量、专家修正样本、Trace日志、模型权重全部留在客户内网
2. 全栈信创适配：海光/鲲鹏CPU、麒麟/openEuler OS、国产数据库
3. 等保三级合规：日志留存不少于180天，支持国密算法SM2/SM3/SM4
4. 审计可追溯：每条结论能回溯到原文精确位置，支持"当时为什么这么判"的秒级回答

## 目标与范围

**设计目标:**
1. 实现8分钟自动审查、1.2小时端到端（含专家复核）的处理目标，效率提升65%
2. 审查准确率95%以上，条款定位准确率从71%提升至94%
3. 跨专家复评结论一致率提升78%，单份token成本下降38%
4. 支持"章—节—条—款"四级结构树重建，每条结论绑定完整证据链
5. 满足等保三级、国密算法、信创适配等合规要求
6. 流程成功率99%以上，支持节点级重试和断点续跑

**不在范围内:**
1. 不追求完全无人化，保留专家最终判断权（半自动模式）
2. 一期不覆盖全部采购方式（聚焦公开招标和邀请招标）
3. 不承诺一期覆盖所有文档类型（但设计可扩展的模板映射机制）
4. 不直接修改模型权重，通过few-shot样本对齐专家尺度
5. 不依赖外部SaaS监控服务，全部私有化部署

## 关键技术决策

### 1. 工作流编排：LangGraph + Celery + PostgreSQL
**理由**：场景核心需求是状态管理、节点级重试、人在回路、断点续跑，这正是LangGraph的设计目标。六节点链路里任何一步失败只重跑该节点，靠的就是状态快照加幂等键。
**替代方案**：
- Airflow：数据管道调度器，强在定时ETL，但不原生支持Agent的有状态循环和人在回路
- Prefect/Dagster：偏数据工程与资产血缘，概念对这个场景是冗余
**补充策略**：用Celery做异步任务队列、PostgreSQL存节点状态快照，LangGraph只负责编排逻辑，避免状态持久化全押在新框架上。

### 9. 前端演示层：FastAPI + Jinja2 + 原生HTML/CSS/JS
**理由**：贴合简历技术栈，不引入React/TypeScript等新框架，保持技术栈简洁统一。Jinja2模板引擎与FastAPI集成良好，原生前端技术确保轻量化和可控性。
**视觉风格约束**：
- **颜色方案**：浅色主题，黑白灰为主色调；红/黄/绿作为业务状态色保留，但使用低饱和度版本（如#dc3545/#ffc107/#198754），禁止渐变、发光、霓虹效果
- **排版规范**：系统无衬线字体（如Inter, -apple-system, BlinkMacSystemFont），不对称栅格布局，充足留白（间距倍数：0.25rem/0.5rem/1rem/1.5rem/2rem）
- **内容克制**：不使用emoji、通用插画和营销文案，保持专业企业感
- **动效限制**：仅使用150-200ms的必要过渡动画（如状态切换、内容展开），无循环动画或复杂特效
**技术边界**：
- 不使用前端框架（React/Vue/Angular）
- 不使用TypeScript或复杂构建工具
- 不使用CSS预处理器（Sass/Less）
- 保持单页应用结构，通过AJAX与后端交互

### 2. 文档处理流水线：PaddleOCR + 自研结构重建
**理由**：中文识别质量好、国产化友好、可完全私有化，这是企业项目的前置条件。
**补齐短板**：PaddleOCR的版面分析相对弱，所以不指望它单独产出四级结构树。做法是PaddleOCR负责文字检测识别，结构树用PDF书签、字体、字号、坐标信息加版面规则重建，复杂件再上版面分析模型辅助，最后人工校验兜底。
**排除方案**：
- Tesseract：免费但中文和版面都要大量调优，工期不可控
- Azure Document Intelligence：效果强，但公有云API和数据不出域直接冲突

### 3. 向量数据库：一期pgvector，信创环境换openGauss DataVec或金仓KES Vector
**理由**：数据不出域、已有PostgreSQL、加事务一致性，证据链和原文是强事务数据，同库最省心。向量规模在条款级（几万到几十万条），pgvector够用。
**技术边界**：pgvector和openGauss的FP32索引都卡在2000维（PG 8KB页面的物理限制）。3072维embedding方案：转halfvec或降维，或选支持更高维的金仓KES（4096维）、达梦DM9（65535维）。
**排除方案**：Milvus性能强但运维重、国产化环境适配复杂；Qdrant和Chroma在国内企业的项目案例弱。

### 4. 大模型路由：可配置网关 + 两级路由，一期不微调
**模型热切换**：通过模型抽象层/网关统一接口，模型名与prompt模板全部配置化。新模型上线先过固定评测集回归，指标达标再灰度切换。
**大小模型边界**：小模型7B-14B本地部署，做预筛、分类、字段抽取；大模型70B以上做主观项判定、冲突推理、报告生成。不按单一参数划，而是按任务复杂度、延迟预算、单次成本三个维度定义。
**微调策略**：一期不微调，用few-shot加prompt工程最快验证价值；二期对高频主观项，用经过质检的专家修正样本做LoRA微调。
**模型选择**：优先选可本地部署的Qwen、GLM、DeepSeek，兼顾信创要求。

### 5. 规则管理：三层结构 + 影子模式更新
**三层存储**：法规层（法律/部门规章）、制度层（企业内部制度）、案例层（历史判例向量化）。每条规则带版本号、生效/失效日期、适用范围、依据原文。
**更新流程**："草稿 → 专家评审 → 影子模式 → 灰度 → 生效"。影子模式下只跑不判定，和人工结论比对一段时间，确认无误再切成判定规则。这样规则更新是运营动作，不需要发版。
**冲突解决**：明确优先级（法规>制度>案例），冲突以规则为准，无原文锚点的结论一律拦截（硬规则）。

### 6. 专家回流：三重防线 + 月度沉淀
**三重防线**：
1. 专家修正必须填修正理由和依据条款
2. 样本入池前做去重、冲突检测、离群点过滤，关键项双人复核
3. 样本带置信度和来源追溯，错误样本可回滚下架
**回流机制**：按月将专家修正沉淀为带依据的few-shot样本，模型不重训也能对齐尺度。这样即使某个样本有问题，影响面可控可撤销，不会污染权重。

### 7. 性能优化：8分钟目标分解
**分解策略**：
- 文档解析（OCR+结构重建）：2-3分钟 → 优化：OCR异步批处理、版面规则前置
- 条款抽取（小模型预筛+模板化）：1-2分钟 → 优化：并行处理、缓存中间结果
- 判定（规则引擎+LLM）：2-3分钟 → 优化：规则引擎并行、大模型批量复核
- 证据绑定+报告生成：1分钟 → 优化：锚点直取、模板渲染
**资源分配**：OCR跑CPU、LLM推理跑GPU，Redis缓存中间结果，小模型预筛降低大模型调用量。

### 8. 合规适配：全栈信创 + 等保三级
**信创适配**：arm64多架构镜像，验证Python二进制依赖（OCR、onnxruntime、numpy）在ARM上的性能。提供CUDA兼容路径承接存量英伟达卡。
**等保三级**：对接企业统一身份认证（OAuth2/SAML/CAS/LDAP），日志留存不少于180天，支持国密算法（SM2/SM3/SM4）的电子签章集成。
**数据安全**：明确"数据不出域"边界清单，外部API调用需显式审批和脱敏处理。

## 风险与权衡

**风险1：OCR识别准确率不足**
- **缓解**：PaddleOCR中文识别质量已验证，自研结构重建算法补充版面分析短板，人工校验兜底，置信度低于阈值时触发专家复核

**风险2：规则覆盖不全导致误判**
- **缓解**：三期规则体系（法规/制度/案例），影子模式验证新规则，专家回流持续补充判例，主观项默认触发专家复核

**风险3：模型推理成本不可控**
- **缓解**：两级路由策略（小模型预筛+大模型复核），token成本实测下降38%，支持按任务复杂度动态选择模型

**风险4：信创环境性能下降**
- **缓解**：提前验证ARM架构性能，提供CUDA兼容路径，性能不达标时可回退到x86+英伟达组合

**风险5：审计可追溯性不达标**
- **缓解**：四级结构树重建+原文锚点绑定，证据链完整存储，无锚点结论硬拦截，支持历史时点规则回溯

**风险6：专家接受度低**
- **缓解**：保留人在回路，专家从通读3.5小时解放到只看可疑点1.2小时，修正理由强制填写，样本可回滚避免污染

**风险7：系统集成复杂度高**
- **缓解**：适配器模式隔离客户系统，异步消息队列解耦，API网关统一对接，核心引擎不感知客户特定逻辑

**风险8：等保认证时间不可控**
- **缓解**：提前进行等保差距分析和密评自查，设计阶段就融入合规要求，预留足够认证时间

## 迁移与实施计划

### 阶段一：原型验证（1个月）
1. 用20-50份真实招标文件验证解析和条款抽取准确率
2. 建立4类场景×10类客观项的规则映射矩阵
3. 分环节性能基准测试，建立P50/P95基线
4. 历史专家结论盲测，计算Cohen's Kappa系数

### 阶段二：MVP交付（3-4个月）
1. 单场景（公开招标）、客观项为主，跑通六节点完整流水线
2. 实现基础的三层规则体系和管理界面
3. 部署在测试环境，与采购系统API对接验证
4. 邀请核心专家试用，收集反馈和修正样本

### 阶段三：扩展完善（2-3个月）
1. 扩展文档类型（技术规格书、合同范本等）
2. 增加主观项审核能力，建立few-shot样本池
3. 完善专家复核工作台和绩效跟踪
4. 部署Prometheus+Grafana+Langfuse监控体系

### 阶段四：信创迁移（1-2个月）
1. 构建arm64多架构镜像
2. 验证国产OS/DB/中间件组合的性能和兼容性
3. 进行等保三级差距分析和密评自查
4. 生产环境灰度发布，逐步迁移流量

### 回滚策略
1. 每个阶段保留完整备份和回滚脚本
2. API版本兼容，新老系统可并行运行
3. 数据迁移可逆，支持快速回退到上一版本
4. 关键业务指标监控，异常时自动告警和人工介入

## 待明确问题

1. **客户具体GPU资源情况**：在没拿到实地信息前，按企业典型画像假设（本地私有化+信创底座为主，叠加少量存量英伟达GPU），需要现场勘查校准
2. **企业统一身份认证具体协议**：需要确认客户实际使用的认证协议（OAuth2/SAML/CAS/LDAP），适配层需要相应调整
3. **电子签章平台集成方式**：需要确认客户既有签章平台的技术接口，或自建CA的具体要求
4. **现有系统API接口规范**：需要获取采购系统、ERP、OA系统的具体API文档，设计适配器实现
5. **专家培训与接受度评估**：需要制定具体的专家培训计划和接受度评估指标，确保系统能真正被使用

这些未知问题不会改变specs、核心架构或任务分解，可以在实施过程中通过与客户沟通逐步明确。
